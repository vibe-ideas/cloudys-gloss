# 专家建议实测：单段批次与有限并行补译

本轮实现并测试了有限并行补译，也对照了保留完整提示词的单段方案。**未发现稳定且通过质量检查的提速，生产默认仍为正文每批两段、串行补译；没有达到全文 30 秒。**

## 实验范围

固定 Cua Driver Bench 文章，81 块、23,126 字符，M4 Pro 上既有 MLX-LM 0.32.0 服务，模型 `Qwen/Qwen3-1.7B-MLX-4bit`、温度 0、总请求并发上限 8。本机缓存 revision 为 `21457c6f51ed54a7c16e988c0844db973815c137`，后两轮显式记入元数据；前四轮未在启动时记录 revision。未替换模型、重启服务或清空服务端提示词缓存。

全部为**模型协议层**计时：包含生成、结构校验与补译，不包含网页滚动、DOM 渲染、OCR 和图片翻译。不能将其与上一轮完整扩展的 56.86 秒直接比较。本轮未进行人工盲审或统计显著性检验。

## 按实际执行顺序记录

| 实验 | 全文耗时 | 初始 / 补译请求 | 结果 |
| --- | ---: | ---: | --- |
| 两段、串行补译 A | 42.70 秒 | 41 / 7 | 基线 |
| 单段、原提示词 | 48.86 秒 | 81 / 13 | 更慢，不采用 |
| 两段、最多两路补译 A | 41.40 秒 | 41 / 7 | 首轮约快 3%，不足以确立收益 |
| 单段、JSON 示例也改为单项 | 50.62 秒 | 81 / 11 | 仍更慢，不采用 |
| 两段、最多两路补译 B | 80.99 秒 | 41 / 7 | 大幅波动，不采用 |
| 两段、串行补译 B | 48.44 秒 | 41 / 5 | 回测也有波动及输出变化 |

每轮都完成 81 块，结构失败计数为 0；这不表示语义准确。除第一轮尚未加入请求计数外，测得的整个响应读取期并发峰值均为 8。实验期间桌面环境未隔离，未收集系统负载时间线；不能把第二次并行补译的慢速全部归因于实现，也不能删除该轮后宣称提速。以上不是严格 ABBA 顺序。

单段方案只改变批大小时使用原有完整专业翻译规则、JSON、流式和校验；它增加了初始请求数，也触发了更多补译。额外实验仅将系统提示词中的双项 JSON 示例改为与单段输入一致，仍未改善全文耗时。没有采用更短的纯文本翻译提示词。

## 质量阻断

两段串行与两段并行补译使用相同模型和提示词，但温度 0 的实际结果仍有变化，不能假定改调度就一定保留逐字输出。

在第 47 块，原文末句是 `agent-desktop completed none of the multi-app tasks in the background.`，串行 A 保留了“未能完成任何多应用任务”，并行 A 却译成“完成了所有多应用任务”，颠倒了否定。该块本身没有补译，因而不能简单归因为补译提示词；目前仅能确认候选运行出现了严重错误。基线也有数字遗漏、术语和段落内容错配，不能将其当作已通过全面质量验收的标准答案。

完整原文、两组译文和运行信息保存在 [summary.json](data/2026-11-09-expert-experiments/summary.json)。这项抽查足以阻止当前候选直接默认启用，不能当作总体准确率。

## 保留的实现

- `OpenAICompatibleProvider` 支持可选请求调度器与每批最多两路补译。调度额度覆盖读取完整响应，包括流式响应体；主请求结束后释放额度，补译重新获取同一个请求池的额度。一项补译失败会取消同批其余补译，取消和超时也会移除排队请求。**生产 `TranslationService` 没有传入该选项，默认仍串行补译。**
- 流解析器保留服务端返回的 usage，诊断可记录 cached_tokens。只有 loopback 测速脚本主动请求 `stream_options.include_usage`，没有给通用网关添加新参数。
- 新增诊断事件 `dispatch` 与 `first-token`，区分请求入队、调用 fetch、收到响应头、首个非空正文片段和完成。首个正文片段可能是 JSON 包装，不等于可读译文。这两个事件在六轮完成后补齐，不能声称已有六轮数据包含完整分阶段时间线。
- 测速脚本记录整个响应期的请求峰值和诊断事件相对整轮开始的时间。它不能代替服务器实际开始生成的时间记录。

并行 A 的 48 个请求合计输入 15,416 tokens，其中报告缓存命中 8,364 tokens，输出 7,100 tokens；已有缓存确实在工作。前两轮尚未采集流式 usage，汇总标为覆盖不全，不能把缺失数据解释为缓存未命中。

## 验证

TypeScript、修改文件的 ESLint、provider / stream / service 的 84 项测试通过。Chrome 与 Firefox 构建通过；两个浏览器各通过 2 / 8 并发大页面和后台暂停续译场景，共 6 项 E2E（27.1 秒），测试使用临时配置文件。本轮没有替换用户已安装的扩展或提交、推送代码。新增单元场景覆盖：

- 请求额度耗尽时超时也会取消排队，额度释放后不再发送过期翻译。
- 两个页面同时补译时共享请求上限，后完成的段落仍按各页原顺序返回。
- 并行补译有一段失败时取消另一段，不继续启动余下段落或发送迟到译文。
- 用户取消补译时移除等待请求，释放请求额度后也不会补发。
- 服务端在译文结束后单独发送用量时保留缓存命中数据，不把统计当成译文。
