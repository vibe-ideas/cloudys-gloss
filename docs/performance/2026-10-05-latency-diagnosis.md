# 翻译等待时间诊断

## 本机复测

2026-10-05，在 M4 Pro 上调用已运行的 mlx-serve 26.10.1，模型为 `Qwen/Qwen3-1.7B-MLX-4bit`，Temperature 0。使用现有六个固定场景，各测两轮；另测六次 HTTP 流解码吞吐。没有启动或重启服务，没有使用插件结果缓存，桌面其他应用保持运行。

这是 provider 层的串行测量，不包含浏览器绘制、插件排队、冷启动，也没有确认用户当前浏览器设置与此端点一致。因此不能将这些数字当作所有网页上的点击到显示耗时。

| 固定场景 | 首个完整译文返回 | 全部完成 | 每次模型请求数 |
| --- | --- | --- | --- |
| reading：两段日常正文 | 0.43 秒 | 0.63 秒 | 1 |
| technical：两段技术正文 | 0.42–0.43 秒 | 0.69–0.72 秒 | 1 |
| article：两段较长正文 | 0.70–0.72 秒 | 1.14–1.23 秒 | 1 |
| bank：语境词卡 | 完整卡片一次返回 | 0.97–0.99 秒 | 1 |
| cloudy：语境词卡 | 完整卡片一次返回 | 6.64–7.53 秒 | 3 |
| light：语境词卡 | 完整卡片一次返回 | 6.06–6.44 秒 | 3 |

HTTP 解码吞吐中位数 **131.5 token/s**，范围 128.7–139.7；首个非空内容片段中位数 **76 ms**。首 token 与完整译文是不同指标。六个场景均通过现有结构校验，不表示本轮重新验证过翻译质量，也不能用两次重复样本估计线上 P95。

## 证据与改进方向

1. **词卡的慢路径最明显。** `cloudy`、`light` 每次均发出三次 HTTP 请求，状态均为 200。结合 `src/provider.ts` 的控制流，这是两次固定例句结构化尝试失败后，进入生成例句的备用路径。第三次非流式请求单独约占 5.1–6.0 秒；不能把全部耗时仅归因于前两次尝试。应先检查失败字段及备用输出，再实验更小的字段修复或分阶段返回，并跑既有语义质量用例。
2. **页面和词卡共享一个队列。** `src/service.ts` 给词卡待执行任务较高优先级，但不会抢占已经执行的页面请求。服务启动参数又固定为 `--max-concurrent 1`。本轮未测量浏览器排队时长；其影响是根据代码推断，仍需滚动、多标签页和边翻译边查词场景验证。
3. **失败批次会重新翻译全部条目。** 页面走流式路径时，整批校验失败会清空临时结果，再逐条非流式重译。可以实验只修复失败条目，但必须先确认 JSON、条目数量及顺序可被信任；不能直接缓存无法确认对应关系的流式片段。
4. **当前已逐段返回，无需再实现一次“整页流式”。** 正文最多两块一批，紧凑组件最多八块一批；首个完整字符串生成后即回传。进一步降低感知延迟可实验段内流式显示，但需要处理临时内容、回滚和布局稳定性。
5. **调度仍有改进空间。** 内容脚本先选可见区，附近 500px 预取；请求进入 background 后通常按队列顺序执行。可以将可见区、预取区优先级传到底层，结合视口变化调整待执行任务，并在相同文本的并行请求之间共享结果。以上均尚未实施或测出收益。

建议先解决词卡长尾，再验证页面优先级与失败条目修复。保留现有质量校验；不直接增加并发，也不以换模型代替端到端测量。
