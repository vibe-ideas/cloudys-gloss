# mlx-lm → mlx-serve：本机迁移与实测

2026-10-05（新加坡时间；原始数据记录 UTC）。本机已把默认推理服务替换为 [ddalcu/mlx-serve v26.10.1](https://github.com/ddalcu/mlx-serve/releases/tag/v26.10.1)，模型仍是 Qwen2.5 3B 4-bit。浏览器 URL、模型 ID、按需启动与登录自启入口保持兼容。[安装与迁移步骤](../guides/model-service.md)

## 结果

| 指标 | mlx-lm 0.32.0 | mlx-serve 26.10.1 初始对照 | mlx-serve 最终托管配置复测 |
| --- | ---: | ---: | ---: |
| HTTP 解码 TPS 中位数（6 次） | 61.0 | 113.7 | 95.4 |
| TPS 样本范围 | 57.8–65.5 | 112.9–114.5 | 75.7–111.8 |
| 测后进程 physical footprint | 2.0 GiB | 1.8 GiB | 1.8 GiB |
| 进程峰值 footprint | 2.3 GiB | 2.3 GiB | 2.3 GiB |
| provider 场景结构通过 | 10/12 | 10/12 | 10/12 |
| 固定译文自动检查（18 例 × 1 轮） | 18/18 | 18/18 | 另一次运行器验证 18/18 |
| 固定译文逐例审阅可接受 | 12/18 | 12/18 | 未另做语义评分 |

初始交叉顺序对照中，mlx-serve 约为原服务的 **1.86 倍 TPS**。切到最终托管配置后的六次读数为 110.6、111.8、111.7、80.2、78.7、75.7，后半程下降明显，因此不能承诺日常稳定 114 TPS。最终复测与初始对照的时间和缓存配置不同，也不能把差异直接归因于缓存上限。未采集温度、功耗或其他进程的 GPU 活动，尚不能确定波动原因。

词卡场景 `cloudy`、`bank` 通过，`light` 在三个服务配置中均两次 Zod 失败。失败也记录在原始结果内，没有剔除。更快的推理服务不能解决模型所有结构输出问题。

## 浏览器实际体验

使用真实生产构建、真实本机服务，两个浏览器串行运行，各一次；全新测试配置没有扩展结果缓存。

| 场景 | Chromium | Firefox Developer Edition |
| --- | ---: | ---: |
| 2,000 段网页：第一段中文显示 | 1,148 ms | 764 ms |
| 首段出现前最大 rAF 回调间隔 | 18 ms | 10 ms |
| 普通页面第一段中文显示 | 2,419 ms | 841 ms |
| 示例完整词卡显示 | 1,449 ms | 1,367 ms |
| 手动启动已停止服务（含生成验证） | 11,927 ms | 13,375 ms |
| 服务已停止时点击翻译到出现中文 | 13,442 ms | 13,451 ms |

大网页测试确认首屏只完成两段时就已显示译文，滚到页尾后继续翻译，关闭可恢复原文。rAF 间隔是短时采样，不能代替完整主线程分析。Chrome 与 Firefox 的数值有运行顺序、前缀缓存等影响，各一次不足以判定浏览器性能高低。

## 质量结论

同一权重的译文基本相近；迁移没有在本次已接受用例上产生退步，但也没有解决已有缺陷。18 条自动检查全部通过，Codex 对照原文、参考答案和语义要求逐条审阅后，两边均只有 **12/18 可接受**，包含 1 条严重错误用例。这是署名审阅，非独立人工盲评，且本轮仅重复一次，不代表广泛稳定性。

具体问题：T02 把读者译为“读取器”；T03/T04 把五年期间的研究译成“比较五个年度”；T06 删除备份的否定条件混乱；T11 留下英文 surprisingly；T18 把转乘译成“连接”。完整译文、参考和评分证据见 [逐例质量对照](2026-10-05-mlx-serve-quality.md)。

固定语料快照、输出、哈希绑定评分与汇总维护在 [tests/quality/baselines/2026-10-05-mlx-serve](../../tests/quality/baselines/2026-10-05-mlx-serve)。它记录已知缺陷，**不表示全量质量门槛已经通过**。不改模型、不改提示词，便于把这次服务迁移与后续模型质量优化分开评估。

## 环境与口径

- Apple M4 Pro，macOS 27.0.1，日常桌面程序保持打开；推理请求串行发送。
- 两边使用 `mlx-community/Qwen2.5-3B-Instruct-4bit`，相同本地 snapshot：`4f83f8f146fdf28b512a06562b671d7af4fab457`。温度 0，未启用 drafter。
- 初始 TPS 对照采用两组相反服务顺序，每组先预热再测三次，预热不计入。旧服务使用原安装配置，新服务使用 8192 上下文、并发 1、前缀缓存 1 条 / 128MB、上游默认 buffer pool。
- 最终托管配置设置 `MLX_SERVE_CACHE_LIMIT=268435456`（256MiB）；其余参数同上。这个变量限制 buffer pool，并不限制权重、活跃张量及整个进程的内存。
- TPS 输入是 `tests/performance/scenarios.json` 中 article 场景，输出上限 1024 tokens。通过 HTTP SSE 的 usage 和时戳计算 `(completion_tokens - 1) / (finish - first_content)`。不等于模型内核解码速度。
- provider 场景复用实际 `translate` / `lookup`、Zod 和回退逻辑，共 6 场景 × 2 轮，无扩展结果缓存。固定质量语料通过实际 provider 流式路径运行，初始对照是顺序采样，未做交叉随机化。
- 内存为 `vmmap -summary` 的进程 physical footprint，输出精度有限；不是权重文件大小、RSS 或整机内存，也不是未来长上下文的硬上限。

原始 TPS 事件、配置与内存快照： [data/2026-10-05-mlx-serve](data/2026-10-05-mlx-serve)。初始结果为 `results.jsonl`，最终托管复测为 `managed-results.jsonl`。测试启动时的元数据未传模型 revision，归档时根据已核实的 snapshot 补充并注明；原始时间戳未改。

## 复跑

安装并启动默认服务后：

```sh
pnpm smoke:mlx
pnpm test:native  # 会真实启停本机服务，勿与推理测量并行
BENCH_SERVICES='[{"name":"mlx-serve-managed","baseUrl":"http://127.0.0.1:8080/v1"}]' \
BENCH_OUTPUT=artifacts/performance/my-mlx-serve \
pnpm dlx tsx@4.23.15 tests/performance/benchmark-services.ts
QUALITY_MODELS=mlx-community/Qwen2.5-3B-Instruct-4bit \
QUALITY_OUTPUT=artifacts/quality/my-mlx-serve \
pnpm test:quality:mlx
```

TPS 脚本只连接显式提供的本机服务，不启动或结束进程；输出目录必须是新目录。比较两个服务时在 `BENCH_SERVICES` 中添加第二个 localhost 地址。质量运行器默认重复两轮，启动独立端口并在结束时清理自身进程，不改 8080 服务。

复现本次审阅报告和无退步检查：

```sh
pnpm quality:report \
  tests/quality/baselines/2026-10-05-mlx-serve/old \
  tests/quality/baselines/2026-10-05-mlx-serve/new \
  --corpus tests/quality/baselines/2026-10-05-mlx-serve/cases.json \
  --baseline tests/quality/baselines/2026-10-05-mlx-serve/old \
  --output artifacts/quality/migration-report.md
```
