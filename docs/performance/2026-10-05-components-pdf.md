# 常见组件、大页面与 PDF 的性能边界

这轮测量关注增加导航、按钮等组件翻译后，正文是否及时显示、请求是否仍受视口约束，以及 PDF 是否增加普通网页负担。使用可控模型响应，不测 MLX 的 TPS 或译文准确率。

## 环境与复现

- Apple M4 Pro、48 GiB 内存，macOS 27.0.1，Node.js 24.14.0。
- Chromium 153.0.8010.12、Firefox Developer Edition 158.0，Playwright 独立临时配置，1100 × 800 视口。
- 每次新建扩展配置和空缓存；本地 HTTP 模型夹具设置 25ms 响应间隔，走真实 background、队列和 provider。
- 原创页面包含 24 个导航链接和 2000 张卡片，每张有标题、正文、按钮，共 6000 多个语义块。一个 worker 顺序执行，每浏览器重复 3 次，采样时不并行运行其他测试。

```sh
pnpm build
pnpm build:firefox
pnpm exec playwright test tests/e2e/performance.spec.ts --repeat-each=3
```

用例和页面在 [performance.spec.ts](../../tests/e2e/performance.spec.ts)、[performance-fixture.ts](../../tests/e2e/performance-fixture.ts)。首段显示时间从触发翻译前计时，到首段插入部分或完整译文；不是模型首 token 延迟。rAF 最大间隔覆盖开启、首段显示、跳到第 2000 张卡片、页尾译文显示的全过程。

测试同时要求：首段正文在前 12 个请求文本内；首屏待处理占位少于 100 个；访问页头与页尾所请求的文本少于 120 块；离屏末段不能提前翻译；关闭后原有 DOM 完整恢复。这些断言不因采样波动放宽。

## 最终实测

双浏览器各 3 次，共 6 次全部通过。采样构建为 `226222f`。逐次数据、无扩展对照和源码 SHA256 归档于 [tests/performance/baselines/2026-10-05-components-pdf.json](../../tests/performance/baselines/2026-10-05-components-pdf.json)。

| 指标 | Chromium | Firefox |
| --- | ---: | ---: |
| 首段显示中位数 | 94ms | 115ms |
| 首段显示范围 | 93.6–138.6ms | 106–118ms |
| 每次采样的最大 rAF 间隔 | 16.8ms | 18.4–18.64ms |
| 模型请求数 | 12–14 | 14–15 |
| 实际请求的语义块数 | 35–45 | 45–47 |

全过程均未记录到 50ms 以上的帧间隔；Chromium 的 Long Tasks 记录为空，Firefox 不提供该项。本结果仅覆盖这台机器、这个页面和这些重复次数，不是跨设备帧率保证。首段时间包含固定响应间隔的模型夹具，不能作为本地 MLX 的真实响应时间。

同样的卡片页面和视口，不加载扩展，独立运行 6 次对照，最大帧间隔约 17–19ms。复现命令（Node.js 24）：

```sh
node tests/performance/baseline-frames.ts
```

### 测量干扰及修正

初次测试曾报告 Chromium 150–167ms、Firefox 350–402ms 的峰值。Chrome CPU 轨迹发现主要耗时来自测试工具的 `ariaSnapshotForExpectFailure → generateAriaTree → getTextAlternativeInternal`；后者一次诊断采样累计约 466ms。核对安装的 Playwright 1.63.0 源码可见，译文 `done` 节点尚不存在时，locator 断言的重试会为整页生成 ARIA 诊断快照。

最终测量改用 `waitForFunction` 定点等待完全相同的 `done + 译文` 条件。计时窗口、正文优先级、请求上限、页尾增量和关闭恢复断言均保留。前述大峰值属于受测试工具干扰的样本，不作为扩展卡顿或这轮优化提升比例的证据。需要重新诊断时，可用 `PERF_TRACE=1` 运行 Chromium 性能场景，输出 CPU 与 timeline JSON；采样值不与带 profiler 的值混用。

## 本轮修正的调度问题

1. Firefox 的两个 IntersectionObserver 回调可能先后到达。正文尚未获得第二个回调时曾被当作屏外，导致两批导航抢先。现在复用附近观察器已经计算的交集，并按时间戳更新可见性，没有新增同步几何读取。
2. 外层扫描虽有 6ms / 200 节点预算，但一次容器文字提取原来会同步检查全部子边界。现在文字读取也可暂停，轮流推进容器和后续子块；大型 main 不再阻挡首段发现。网页在挂起期间改字会使旧读取重启，不拼接过期内容。
3. 裸链接组的分类结果在扫描上下文中缓存，宿主变更后失效；不再对每条链接反复分类同一组。正文、短组件分别分批，并交替进入队列。

帧间隔只能说明观察到的响应间隔，不能直接归因给某个函数。测试额外保存跳转时点和超过 50ms 的帧间隔；支持 Long Tasks 的浏览器另保存该 API 的条目。没有条目也不能证明所有工作都没有阻塞。

上一份 [2000 段报告](2026-10-04-large-page.md) 使用真实 MLX、简单段落，并只记录首段出现前的帧间隔。这次页面、模型和采样窗口都不同，不能把两份数字直接作为性能提升比例。

## PDF 的资源控制

- PDF.js、解析 worker、字体与字符映射只从独立阅读器加载，不进入普通网页内容脚本；所有资源随包提供，无 CDN 请求。
- 采样构建的双端内容脚本均为 73,433 字节；PDF 字体、字符映射和解码器共 2,590,571 字节，完整扩展每端约 8.16 MB（未压缩）。包体积包含既有词典等资源，不等于运行内存。
- 文件最多 40 MB，下载在无 Content-Length 时仍执行流式大小上限；取消和超时会停止读取。
- 同时仅保留一个活动页画布，最高 300 万像素。切页或关闭销毁旧页任务，关闭文档终止 worker。这个像素限制不是浏览器进程的总内存上限。
- 当前页最多提取 200 段或 100,000 字符，最多 8 段 / 5000 字符一批，逐段回传；不会预先翻译整本 PDF。单页所有段落仍会依次请求，密集页可暂停。
- 原创 20 页 PDF 验证取消、切页、错误恢复和窄屏；Mozilla 公开 14 页论文在两种浏览器均提取并返回第一页的 57 段，390px 无横向溢出。使用固定模型译文，不评价语言质量。

## 保留的限制

`TranslationLayout.gridOverlaps` 为判断自动网格能否安全增高，仍同步测量全部直接子项并排序；这条路径尚未分片。当前 2000 张卡片夹具使用普通文档流，不能为拥有数千直接子项的大型 CSS Grid 背书。只检查附近项目便修改整张网格会误改显式行列布局，因此本轮没有采取这种简化。

6ms 是初扫分片预算，不是所有 DOM 工作的耗时上限。附近块的样式可见文字核对、流式结果的原文核对仍同步读取单个语义块；带直接正文且同时包住大量子块的特殊容器仍可能较重。

本轮没有采集 PDF 浏览器进程峰值内存，也没有覆盖扫描件 OCR、所有复杂网格或所有网站。自动化结果和资源上限不能表述为“所有网页持续 60fps”或“整个 PDF 只用几 MB”。
