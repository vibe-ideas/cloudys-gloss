# M4 Pro：MLX 与 llama.cpp 对比

日期：2026-10-04。结论：在这组翻译输入上，MLX 比 llama.cpp 更快；但当前 MLX 3B 的词卡结构和内容质量存在问题，不能仅按速度判断可用性。

## 环境与方法

- Apple M4 Pro，48 GiB 统一内存，接电；Darwin 27.0.0。
- MLX 0.32.3 / MLX-LM 0.32.0；模型 `mlx-community/Qwen2.5-3B-Instruct-4bit`，4-bit、group size 64。
- llama.cpp 0.5.0，build 11146，commit `7fe450e19`；官方 Qwen2.5-3B-Instruct GGUF Q4_K_M，Metal 全层卸载、Flash Attention、4096 上下文。
- 温度 0、请求串行。每种缓存模式按 MLX → llama → llama → MLX 顺序测量，每块 2 轮、每轮 6 种输入，共 96 次 provider 调用。
- 3 组双段翻译；`cloudy`、`bank`、`light` 三个上下文词卡。每模型、每缓存模式、每场景 4 次，表中为中位数。
- 调用项目真实 `OpenAICompatibleProvider`，包括流式解析、Zod 校验、回退和重试；无 IndexedDB 结果缓存，无浏览器 DOM 渲染和排队。
- uncached 关闭后端提示词复用；cached 开启各后端原生 prompt cache。二者缓存机制并不完全相同。

模型 revision、GGUF SHA-256、完整输入见 [metadata.json](data/2026-10-04-backends/metadata.json)。两种量化权重并非逐位一致，因此这是实际配置对比，不能把全部差异归因于推理框架。

## 无提示词缓存的延迟

单位：毫秒。

| 场景 | MLX 首段 | llama 首段 | MLX 完整 | llama 完整 |
| --- | ---: | ---: | ---: | ---: |
| 日常阅读，两段 | 481.5 | 511 | 704 | 816.5 |
| 技术说明，两段 | 920 | 1005.5 | 1957 | 2020 |
| 较长文章，两段 | 969 | 1060 | 1589 | 1717.5 |
| cloudy 词卡 | — | — | 1269 | 1580.5 |
| bank 词卡 | — | — | 1009.5 | 1117.5 |
| light 词卡 | — | — | 2412.5，全部失败 | 1495.5 |

技术说明在两后端都触发了批次 JSON 回退：一次批量请求后，再发两次单段纯文本请求。表中已计入这三次请求；这是优化完整耗时的重要方向。

开启提示词缓存后，日常阅读首段分别为 340 / 403 ms，完整耗时为 552.5 / 703 ms。全部分场景结果见 [by-scenario.json](data/2026-10-04-backends/by-scenario.json)。

## 可靠性与质量

两种缓存模式合计：全文翻译两后端均为 24/24 通过结构与中文存在性校验；词卡 MLX 16/24，llama 24/24。MLX 的 `light` 在重试后仍返回不合法结构。

这只是三个词各重复八次，不是词典准确率。人工检查还发现 MLX `cloudy` 缺少 IPA、词性错误和占位式上下文；llama 的 `cloudy` 也有错误 IPA、混入“晴朗”的释义，`light` 的词性与含义不一致。结构通过不能代替内容质量评估。

## 内存

| 后端 | 进程 physical footprint | vmmap 总 resident |
| --- | --- | --- |
| MLX，无 prompt cache | 约 1.9 GiB | 约 2.4 GiB |
| MLX，有 prompt cache | 约 2.1 GiB | 约 2.5 GiB |
| llama.cpp | 约 289–347 MiB，未完整计入映射权重 | 约 2.7 GiB |

llama.cpp 另有约 1.9–2.0 GiB resident 映射文件，不能说它只占 300 MB。总 resident 包含共享库，并非独占物理内存；不同分配方式下只比较 footprint 会误导。见 [内存摘要](data/2026-10-04-backends/memory-summary.json)。

## 复现

需要已安装 `llama-server`、MLX Python 环境、上述 GGUF 和 MLX 权重；先停止其他模型推理，脚本自身只同时启动一个后端。

```sh
MLX_PYTHON=/path/to/mlx-env/bin/python \
GGUF_MODEL=/path/to/qwen2.5-3b-instruct-q4_k_m.gguf \
pnpm dlx tsx tests/performance/benchmark-backends.ts
```

固定测试工具版本可使用 `pnpm dlx tsx@4.23.15`。支持 `BENCH_OUTPUT`、`BENCH_ORDER`、`BENCH_MODES`、`BENCH_REPEATS`、`BENCH_CASES`；默认在本地 18080 端口顺序启动后端。输出写入 `artifacts/benchmark/`。

## 限制与数据

测试时日常应用未关闭；一轮 lint/typecheck/unit test 与最后一块 uncached MLX、第一块 cached MLX 有短暂重叠。启动计时含操作系统暖磁盘缓存，不是真正重启后的冷启动；未测高并发、长上下文和功耗。LM Studio 未安装，本报告不能用于声称某个 GUI 快或慢。

原始流式分支没有完整保存最终 usage，不能从这份历史记录可靠推导 MLX TPS；TPS 单独见 [补测报告](2026-10-04-mlx-models.md)。
