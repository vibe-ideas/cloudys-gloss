# 翻译速度：竞品调研与三路专家审查

日期：2026-10-05。范围：全文翻译、划词词卡、跨标签页调度与等待体验。

## 结论与证据范围

优先减少重复推理、让当前阅读任务优先，并改进词卡慢路径。现阶段不建议直接增加并发或换模型。

本轮由性能与模型请求、浏览器调度、UX 交互三个独立专家代理进行只读审查；主线程核对官方产品资料与 TWP 开源实现。没有安装或跑同设备竞品性能对照，因此不能声称我们的速度比任何竞品快或慢；产品宣传中的“即时”也不作为耗时证据。

本机量化依据沿用 [延迟诊断](../performance/2026-10-05-latency-diagnosis.md)：正文首个完整译文 0.42–0.72 秒；正常词卡约 0.98 秒；慢词卡 6.06–7.53 秒。后者连续请求三次，其中第三次备用生成单独占约 5.1–6.0 秒。不是仅减少前两次请求就能变为一秒。

## 专家发现与实施顺序

以下为提议，尚未实现；收益必须用端到端实验确认。

### 1. 先补慢路径观测，再优化词卡修复

**已证实：** 当前测量只记录请求次数和响应头时间，没有记录每次失败字段、输出 token 数和结束原因。`src/model/provider.ts:148–160` 在两次固定原句尝试失败后进入备用生成；两轮 `cloudy` 最终结果都包含不含该词的第二例句。现有 schema 允许多个例句，因此结构成功并不代表语义达标。

先补每次尝试的阶段、校验问题、用量和完整响应耗时。然后实验保留固定原句、仅修复错误字段、限制不必要的备用输出。修复后仍完整校验并跑质量集，不能靠忽略错误或直接跳过固定例句路径提速。

另一个等待上限问题：`structured()` 每次调用单独计时。固定例句与备用生成两条路径串行时，整体理论上可能接近两倍配置 timeout，还不含排队。需要独立定义整次操作的 deadline；这是限制最坏等待，不是提升 TPS。

### 2. 让后台调度理解用户当前操作

**已证实：** `src/page/translator.ts:406` 的可见优先只发生在页面内；`src/model/service.ts:29` 把页面请求加入普通队列。手动重翻没有传递交互优先级；`src/core/queue.ts:23` 的 priority 使用 `unshift`，同档任务后进先出。隐藏标签页没有暂停新增任务的机制。

建议按“用户主动查词/重试 → 可见内容 → 附近预取”排序；同级先到先执行，并有防止低优先任务长期等待的规则。标签页隐藏后暂停新增预取、退让尚未执行的低优先任务；切回后增量恢复。初版不频繁中断已经生成中的有效请求。

**尚未测量：** 多标签下排队贡献多大，及取消能否立即释放上游推理资源。不能把页面取消 Promise 等同于服务已经停止生成。

### 3. 消除跨请求重复推理

**已证实：** `src/model/service.ts:15–29` 只有单批去重，缓存只在排队前读取。多个页面同时冷请求相同文本时，后来的任务可能在第一份结果已缓存后仍继续推理。

低成本实验是实际执行前再次检查缓存；完整方案为同 cache key 共享进行中任务。缓存落盘与 flight 移除必须正确衔接。每个订阅者独立取消，全部取消才中止上游；模型、语言、配置、词卡上下文不同不能误合并；显式重翻不能被旧任务吞掉。

### 4. 保留成功段落，只修复可确认的失败项

**已证实：** `src/model/provider.ts:65–66,103–117` 会在整批校验失败后撤回所有临时译文，随后逐条非流式重译。这既浪费成功条目的生成，也造成“出现 → 消失 → 再出现”。

仅在完整 JSON 可解析、数量及对应关系可信时复用有效条目，失败项单独修复。整体截断、数量错误、映射不明时不能把部分流式片段当正式结果。手动重翻已有保留旧译文的行为，应继续保持。

### 5. 点击词卡后先给可用内容，并说明实际等待阶段

**已证实：** 离线音标虽然与模型并行读取，但 `src/model/provider.ts:161–163` 等完整词卡后才返回；整个 lookup 又在 `src/model/service.ts:55` 排队。`src/ui/popover.tsx:144` 在不同等待阶段一直显示相同提示。

用户点击小组件后，离线音标可绕过模型队列先返回，并提供现有发音能力；释义和例句完成验证后再补入。后端应发送真实的等待/生成/补全阶段，不能用假进度条或预估倒计时掩盖等待。缺失音标不生成假值。

分阶段显示须保持卡片方向和位置稳定，限制高度并在内部滚动，避免每次增长都从选区下方跳到上方。动画不能算实际加速指标。

## 已有能力与不应直接采用的做法

当前已有语义分块、500px 附近预取、可见区优先、正文两块/组件八项批量、1800 字符上限、逐段返回、24ms 合并绘制、SPA 增量扫描、缓存和取消。无需重新实现一套同名机制。

- 不直接把插件 concurrency 改大：本机 mlx-serve 启动参数仍为 `--max-concurrent 1`，可能仅把排队搬到服务端。
- 不照搬竞品排除导航的默认范围：用户明确要求常见组件完整覆盖。
- 不把 Google/DeepL 云服务的速度当作本地小模型 LLM 的同条件基准。
- 不放宽质量要求换成功率，不让未验证的 AI 字段进入正式缓存。
- 不全页逐 token 重绘；段内流式需另测布局稳定性和主线程成本。

## 下一轮固定验收场景

用例仍放 `tests`；下表是待实现清单，不表示本轮已新增或通过。

| 场景 | 应满足的行为 | 记录指标 |
| --- | --- | --- |
| 三个标签页冷缓存翻译，连续切到最后一页 | 当前页优先；隐藏页暂停新增低优先工作；返回旧页保留进度 | 前台首段延迟、隐藏页请求数、排队耗时 |
| 页面翻译中主动查词或重翻 | 当前任务完成后，交互先于待执行预取；同级 FIFO，不饿死正文 | 点击到首个可用内容、整卡延迟、执行顺序 |
| 两页同时翻译相同段落 | 相同配置仅一次上游推理；一页取消不影响另一页 | 上游次数、取消后有效结果、配置隔离 |
| 批量两段中只有一段校验失败 | 对应关系可信时保留成功段，只修失败段 | 回滚次数、重译次数、布局跳动 |
| 批次 JSON 截断或数量错乱 | 不留下无法确认对应关系的正式译文 | 错配数量、失败恢复行为 |
| 词卡 AI 延迟 8 秒且排队 3 秒 | 点击后离线音标先可用；阶段真实；关闭及换词无迟到污染 | 点击反馈、音标出现、完整卡片耗时 |
| 快速滚到底部后往返滚动 | 过期待执行预取退让，无持续取消重启 | 新视口首段、浪费生成量、重复请求数 |
| 靠近屏幕边缘、200% 缩放、减少动画偏好 | 卡片逐步补内容不越界、不突然换边，键盘可关闭 | 位置变化、交互可达性 |

先用可控 mock 验证调度与取消，再用同一真实 MLX 服务验证 Chrome/Firefox 点击到显示。区分缓存、排队、模型、绘制耗时；空缓存与热缓存分开报告。收集足够样本后再统计 P50/P95，同时回归已有翻译质量集及独立样本。
