# YouTube 字幕同步：竞品参考与验收标准

调研日期：2026-10-18。

## 官方资料确认了什么

[沉浸式翻译 FAQ](https://immersivetranslate.com/docs/faq/) 的视频章节提到 YouTube 自带机翻字幕的格式问题，并提供“使用沉浸式翻译来翻译 YouTube 字幕”选项。因此可以确认它支持平台机翻与扩展翻译服务两条路径，不能把所有同步表现都归因于 LLM 推理速度。

[官方 GitHub 仓库](https://github.com/immersive-translate/immersive-translate) 明确说明当前产品并非开源，仓库用于版本分发和问题反馈；旧开源项目于 2023-01-17 归档。未取得当前内部调度的证据，不能声称已确认它使用多少并发、提前缓存多少秒或具体重试算法。

## 本项目采用的实现

先获得包含时间戳的原始字幕，再优先翻译当前位置，连续分批填充后续缓冲；播放过程中按视频时钟取已确认译文。新增被动复用播放器原始响应，覆盖用户点击双语之前已下载字幕的情况，避免完全依赖再次请求相同地址。资源边界与生命周期见 [字幕设计](youtube-subtitles.md)。

实时 CC 只有已经播放的文字。对这条路径，减少防抖、自动重试和补齐历史可以改善体验，却不能保证每句开始时已有译文。界面明确显示降级状态和连续缓冲秒数，不能把历史最终补齐率叫作同步率。

平台中文字幕或平台自动翻译是可选的后续方向：如果用户接受 YouTube 云端翻译，可提前取得中文轨道并与原文按时间对齐，跳过本地模型的逐句生成。当前补丁没有启用这一数据路径，也没有改变本地优先设置。平台轨道可用性、翻译请求失败和拖动后的行为仍需实际验证，不能承诺无条件零延迟。

## 同步验收

- **按时可用率**：每条字幕开始时，完整且已校验的译文是否已就绪。流式首字和播放结束后补入历史均不算。
- **冷启动**：从开启到首句就绪、到获得足够连续缓冲，分别记录耗时。
- **持续播放**：同一视频在 1 倍 / 2 倍速持续播放，记录缺译句数、最长缺译时间和缓冲最低值。
- **拖动与切换**：拖到缓冲外、切字幕语言、SPA 换视频后，不能错配旧译文；恢复耗时单独统计。
- **来源**：区分真实模型、模拟服务和平台字幕，不能跨来源比较延迟或通过率。

固定延迟回归已验证完整轨道在预译 5 秒后可连续同步；它只证明调度在设定吞吐下能跟上，不能代表用户当前模型或 YouTube 网络实测。结果见 [性能记录](../performance/2026-10-18-youtube-subtitles.md)。真实站点尚待用户重新加载构建后的连续观看验收。
